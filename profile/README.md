<h2>二、要不要上池、池多大、怎么分组</h2>
<h3>第一题：先看账号价值</h3>
<p>绑定年付订阅、有历史对话积累、涉及真实业务的账号，优先独享，别进池。纯测试、临时任务、用完即弃的账号，进池更经济。介于两者之间的，用混合方案：核心账号独享，边缘任务池化。</p>
<h3>第二题：按环境数定量，不按人头</h3>
<p>出口数量取决于"需要互相隔离的环境数"。十个人共用一个账号体系，一条出口就够；两个人各自独立账号，就是两条。常见误区是按人数买线，结果一半闲置。</p>
<h3>第三题：分组方式只选一种为主</h3>
<p>地区优先适合账号资料分属多国；业务优先适合多人协作、任务边界清晰。可以两级，但主维度只能有一个，否则台账两周就乱。分组名建议写成「地区-业务-序号」，例如 us-content-01，一眼能看出归属。</p>
<h2>三、复用上限与轮换规则</h2>
<p>单出口挂几个账号，是池化里风险最集中的一项。挂得越多，单点故障的连带面越大；挂得太少，成本压不下来。经验区间是：高价值账号一出口一号，中价值不超过 3 个，低价值测试号可到 5 个，但要接受"一出事就整批处理"的代价。</p>

<h3>轮换要看触发条件，而不是日历</h3>
<p>定期轮换（比如每月一次）看起来整齐，实际上会在毫无必要时打断稳定环境。更合理的做法是触发式：出口 IP 漂移超过设定范围、连续探活失败、同段邻居密度骤增、账号出现连续验证，满足任一条件才换。</p>
<h3>轮换要留过渡期</h3>
<p>换出口不是切开关。新出口先单独跑 24 小时探活，确认稳定再切账号；切换后头两天降低操作频率，观察是否出现额外验证。整个流程写进 SOP，避免每次靠人记。</p>

<h2>四、监控口径与退出机制</h2>
<h3>监控只留四个指标</h3>
<p>端口可用率、出口 IP 变化次数、验证码触发率、平均响应时延。前两个脚本采，后两个半自动记录。指标超过阈值就告警，告警要落到人，不能只发到群里没人认领。</p>
<h3>退出机制提前写</h3>
<p>三个信号出现两个，就该考虑退出当前池：连续两周在线率低于 99%、同段邻居密度明显上升、服务商响应时间超过承诺。退出时要做的动作也提前写清：账号迁移顺序、旧出口保留多久、台账如何标记。</p>
<h2>五、把答案写成一页台账</h2>
<p>七道题的答案最后要落成一张表，字段不用多：账号标识、绑定出口、分组标签、绑定日期、最近异常、下次复核日。每周更新一次，每月复盘一次，谁改谁留名。</p>

<h2>常见问答</h2>
<h3>十几个账号一定要用池吗？</h3>
<p>答：不一定。如果账号价值高、资料分散，一号一线的独享方案更省心。池化的价值在于承接低价值、高频更换的任务，不是规模大了就必须上。</p>
<h3>一个出口挂三个号，风险有多大？</h3>
<p>答：取决于这三个号的关系。同业务、同地区、资料自洽的三个号，风险可控；跨地区、跨业务的混挂，一旦出口出问题，处理起来要分开判断，成本会翻倍。</p>
<h3>定期轮换和触发式轮换，哪个更好？</h3>
<p>答：长期稳定场景优先触发式，避免无谓打断；短期任务密集的场景可以定期批量替换，省去逐个判断的精力。两者可以并存，按账号价值分层。</p>
<h3>台账要记多细才够用？</h3>
<p>答：六列够起步。关键是"最近异常"和"下次复核日"这两列要真的填，其余字段用于定位。宁可字段少但每周都更新，也不要字段多却三个月没动。</p>
